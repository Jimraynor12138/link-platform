# 技术点与面试素材

> 用途：把项目实践中的**技术取舍、踩坑、原理**沉淀成可面试复述的素材，避免"代码写了但讲不出来"。
> 每条包含：**现象/结论 → 原理 → 面试话术**。持续追加。

---

## 一、多模块与解耦

### 1.1 公共模块的"最小依赖集合"

- **结论**：`link-common` 只依赖 `spring-web`（**不是** `spring-boot-starter-web`）+ `spring-context` + `slf4j-api` + `jackson-databind` + `lombok`。
- **原理**：`link-gateway` 是 WebFlux 反应式的，若 common 引入 `spring-boot-starter-web`，会经传递依赖把 Tomcat 与 `WebMvcAutoConfiguration` 拖进网关，导致网关启动失败。
- **补充踩坑**：`GlobalExceptionHandler` 里 `MethodArgumentNotValidException` 继承自 `spring-context` 的 `BindException`，而 `spring-web` 并不传递 `spring-context`；`@Slf4j` 生成的 `log` 需要 `slf4j-api`。这两个依赖必须显式引入。
- **面试话术**："公共模块不能什么都往里塞。我先确认了它的**消费者**——包括一个 WebFlux 网关，所以依赖面上刻意避开 `starter-web`，只用 `spring-web` 借注解。踩过一次坑：异常处理类因为 `BindException` 在 `spring-context` 里而编译失败。"

### 1.2 包名不变 ⇒ 零 import 改动

- **结论**：跨模块搬类时**保留原包名**（`com.shortlink.common.*`），消费方一行 import 都不用改。
- **原理**：Java 的编译期依赖看的是"类的全限定名 + 是否在 classpath 上"，与"类在哪个 jar 里"无关。包名不变 + 目标模块声明了依赖，就等价于原地不动。
- **面试话术**："我把 4 个公共类从 core 搬到 common，但保留包名，所以 96 个文件的 import 一行没改，198 个单测直接绿。如果同时改包名，就得面对'搬目录'和'改 import'两个变量的叠加，排查成本翻倍。"

### 1.3 "为抽而抽"的边界

- **结论**：`ClientIpResolver`（依赖 `jakarta.servlet.http.HttpServletRequest`）留在 core，不搬 common。
- **原理**：servlet API 在 WebFlux 里根本不存在，放进公共模块会把 servlet 依赖拖进网关；且它只被 servlet 侧的统计链路使用。
- **另一例**：`DegradedException` 本来计划留 core，但 `GlobalExceptionHandler`（搬去了 common）引用了它 → 必须**联动搬走**，否则形成 `common → core` 反向依赖。
- **面试话术**："抽公共类的判据不是'看起来通用'，而是'谁真的要用它'。边界感比抽得多更重要——抽错了要么引入依赖污染，要么制造反向依赖。"

### 1.4 `spring-boot-maven-plugin` 的位置

- **结论**：必须放 parent 的 `<pluginManagement>`，并只在**可运行模块**的 `<build><plugins>` 里激活。
- **原理**：若直接放 parent 的 `<build><plugins>`，会被所有子模块继承；`link-common` 没有主类，`repackage` 会报 `Unable to find main class` 而构建失败。
- **面试话术**："多模块里 `pluginManagement` 和 `plugins` 的区别是：前者只给配置、各模块按需启用；后者是直接继承。可执行 jar 的插件放在前者，common 才不会被误打包。"

## 二、缓存与防穿透

### 2.1 布隆过滤器：自写本地位图 vs Redisson RBloomFilter

- **结论**：项目**手写**布隆过滤器（`BloomFilterHash` + `BloomBitmapStore` + `ShortLinkBloomFilter`），不用 Redisson 的 `RBloomFilter`。
- **原理**：
  - `RBloomFilter` 数据在 Redis，每次 `contains()` 都是一次网络往返；而跳转链路对延迟极敏感。
  - 自己实现改为：启动时把位图（1MB 级）**一次性加载进进程内存**，查询在本地数组完成（**零 RTT**），Redis 只做整块加载与"本地判不存在"时的回查确认。
  - 历史教训：旧实现每次 `mightContain` 要对 k=7 个下标逐个 `GETBIT`，**每个跳转请求 7 个 Redis RTT**，比它要省掉的那次缓存查询还贵，还把 L1 本地缓存彻底架空。
- **自写的代价**：本地位图牺牲了"跨实例强一致"→ 必须补"本地判不存在时回查 Redis 确认"，否则会把其他实例刚创建的短码误判 404（fail-close 事故）。
- **注意区分**：Redisson 在这个项目里用在**分布式锁**（替换手写 SETNX，要可重入/看门狗续期），不是布隆过滤器——两个方向相反的取舍。
- **面试话术**："布隆过滤器我刻意自写，因为跳转要零 RTT，Redisson 每次查 Redis 吃不下；分布式锁我准备换成 Redisson，因为要可重入和续期，手写 SETNX 做不到。"

## 三、认证与授权

### 3.1 JWT 撤销：黑名单 key 用 `jti` 而不是整个 token

- **结论**：JWT 里加 `jti`（token id），登出时把 `jti` 作为 Redis 黑名单 key。
- **原理**：JWT 自身无法撤销（签发即有效）。常见解法是"按剩余有效期把 token 放进黑名单"。若用**整个 token 字符串**当 key（200~300 字节），Redis 内存浪费明显；用 `jti`（短、唯一）更合理。
- **面试话术**："JWT 撤销我用黑名单实现，但 key 不用整个 token——token 有两三百字节，当 key 很浪费；我在签发时埋了 `jti`，用它做 key，TTL 设成 token 剩余有效期，到期自动清。"

### 3.2 双 Token + 刷新轮换

- **结论**：Access Token 短（30min）+ Refresh Token 长（7d，存 Redis）。
- **解决的问题**：Access Token 过期后，用 Refresh Token 换新的，避免用户重新登录；同时 Access Token 短有效期降低了泄露风险。
- **轮换防重放**：刷新时把传入的 refresh 与 Redis 中的当前值**比对，不等即 401**——旧 refresh 用一次就失效，防止被窃取的 refresh 反复使用。
- **面试话术**："刷新不只是'换新 token'。我在 Redis 里只保留**最新的** refresh，刷新时比对，不是最新的一律拒绝，这样旧 refresh 被偷了也用不了（轮换防重放）。"

### 3.3 刷新时重新加载用户与权限

- **结论**：刷新流程重新走一次"加载用户 + 权限"，禁用用户会抛 `DisabledException` 无法续期。
- **取舍**：代价是每次刷新多一次 DB 查询；收益是"禁用即时生效、权限变更即时生效"。
- **面试话术**："刷新时我是重新查库加载权限的，不是从 token 里直接取。多一次 DB 查询，换来禁用用户无法续期、权限变更立即生效。"

### 3.4 401 与 403 分离

- **结论**：未认证走 `AuthenticationEntryPoint`（401），已认证但无权限走 `AccessDeniedHandler`（403）。
- **原理**：两者语义不同，客户端处理方式也不同（401 去登录，403 提示无权限）。

### 3.5 多租户越权防护

- **结论**：`tenant_id` 的唯一可信来源是 **Token**，由服务端解析后注入 `TenantContext`（ThreadLocal），业务代码只从上下文取值；**永不接受前端传入的 tenant_id**。
- **必做的清理**：请求处理完在 `finally` 里 `clear()`——线程池复用会串租户，这是最隐蔽的越权 bug。
- **面试话术**："多租户最怕越权。我的原则是 tenant_id 只从 token 解析、服务端强制注入，前端传什么一概不信；而且 ThreadLocal 必须在 finally 里清理，否则线程复用会把 A 租户的身份带给 B 租户的请求。"

## 四、配置与中间件

### 4.1 配置 vs 常量：隔离手段为什么不同

- **现象**：RabbitMQ 拓扑名可以靠改 yml 隔离，Redis key 前缀却改不掉。
- **原因**：`RabbitMqConfig` 全程读 `LinkCoreProperties`（配置驱动，无硬编码）；而 `CacheKeyBuilder` 里 `link:core:link:` 等前缀是**硬编码常量**。
- **结论**：Redis 的隔离只能靠**换 database index**（AAF 用 db 1，AAE 用 db 0）。
- **面试话术**："两个项目共用一套 Redis 时，改 key 前缀最干净，但我们的前缀是硬编码常量改不动，所以直接换 db 隔离。这反过来提醒我：哪些东西该做成配置、哪些该固化成常量，是要提前想清楚的。"

### 4.2 `tomcat-embed-el` ≠ Servlet 容器

- **现象**：依赖审计时 `link-gateway` 的依赖树里出现了 `tomcat-embed-el`。
- **辨析**：它是 **EL 表达式库**，由 `spring-cloud-gateway-server → spring-boot-starter-validation` 带入，用于校验消息的 EL 表达式；**不是** `tomcat-embed-core`（Servlet 容器）。
- **判定红线**：网关不能有 `spring-webmvc` / `tomcat-embed-core` / `jakarta.servlet`——这三者才是"会与 WebFlux 冲突/启动 Tomcat"的东西。

### 4.3 MQ 选型：JD 要的是通用原理，不是某个 API

- **结论**：保留 RabbitMQ 作为已实现基线，P5 做统计链路 MQ 抽象，Kafka 作为第二实现（可切换）；不引入 RocketMQ。
- **理由**：MQ 的通用原理（幂等、死信、顺序、丢失/重复、消费组/分区、吞吐 vs 可靠性）才是面试考点，项目里已有载体（`IdempotentChecker` 幂等、DLQ 死信、重试 3 次）。
- **面试话术**："统计链路我把 MQ 抽象成可切换的接口，RabbitMQ 和 Kafka 各实现一份。与其背某个 MQ 的 API，我更愿意讲清楚——幂等怎么做、死信怎么配、为什么这样选。"

### 4.4 基础设施 vs 业务服务的容器化策略

- **结论**：基础设施（Kafka/Nacos/Sentinel）用 Docker Compose；MySQL/Redis/RabbitMQ 沿用本地；业务服务开发期本地 run，**P7 才统一打镜像编排**。
- **理由**：基础设施"装一次用很久"、本地装 Kafka/Nacos 折腾；业务代码频繁改，每次打镜像是浪费。
- **镜像做法（P7）**：`spring-boot-maven-plugin` 的 layered jar + 多阶段 Dockerfile，镜像分层、构建缓存友好。

## 五、工程与验证方法

### 5.1 测试基线口径必须精确

- **结论**：AAE 基线是 `Tests run: 198, Failures: 0, Errors: 0, Skipped: 1`。
- **原理**：那 1 个跳过是 `IdGeneratorBenchmarkTest`，带 `@EnabledIfSystemProperty(shortlink.benchmark=true)`——**设计上默认不跑**（压测基准需 MySQL/Redis）。
- **原则**：不能写成"198 全绿无跳过"。讲数据要精确到 skip 这种细节，否则被追问就穿帮。

### 5.2 三个安全点（重构验证方法）

- **做法**：①原仓库跑测试拿基线 ②原样复制后再跑（证明"复制无损"）③抽公共类/改 import，每改一批跑一次。
- **原理**：**一次只引入一个变量**，任何一次变红都能立刻定位是哪一步引入的。
- **面试话术**："我做这次迁移分了三步，每步都跑测试：先在原仓库拿基线，再原样复制后跑一次证明搬迁没影响，最后才抽公共模块。这样任何一次失败我都能立刻知道是搬迁的锅还是重构的锅。"

### 5.3 多项目共享环境时的隔离清单

| 资源 | AAE（旧） | AAF（新） |
|---|---|---|
| MySQL 库 | `short_link` | `link_platform` |
| Redis | db 0 | db 1 |
| RabbitMQ 拓扑 | `short-link.visit.*` | `link.visit.*` |
| 服务端口 | 8080 | gateway 8080 / auth 8081 / core 8082 / stats 8083 |

- **为什么要隔离**：两个项目要能同时跑（P7 要并排压测），且 P4 给 core 加 `tenant_id` 时不能污染旧库基线。
- **不复制旧数据的理由**：旧数据没有 `tenant_id`，复制过来反而要写迁移脚本；新库建空表，用接口造数即可。

## 六、认证链路（V1 实践）

### 6.1 `@PreAuthorize` 的 403 必须自己兜

- **现象**：只读账号访问 `@PreAuthorize("hasAuthority('user:manage')")` 的接口，返回的是 **HTTP 200 + 业务错误码**，看起来像"成功"。
- **原因**：`@PreAuthorize` 抛出的 `AccessDeniedException` 发生在 **DispatcherServlet 内部**，位置比 Spring Security 的 `ExceptionTranslationFilter` **更靠里**，因此不会被 `AccessDeniedHandler` 捕获；随后被全局兜底的 `@ExceptionHandler(Exception.class)` 吃掉。
- **后果**：**事实上的鉴权失效**（前端把 200 当成功），且单测抓不到（不启 Spring 上下文），只有 E2E 能发现。
- **解决**：单独写一个 `@RestControllerAdvice` 处理 `AccessDeniedException` 返回 403。注意**不要放进公共模块**——common 的依赖白名单里没有 spring-security。
- **面试话术**："用 `@PreAuthorize` 要注意它的拒绝异常不走 Security 的异常转换链，如果你有全局兜底异常处理器，会把它变成 200。我是靠 E2E 才发现这个漏洞的。"

### 6.2 刷新接口必须免认证

- **结论**：`/auth/refresh` 必须放进白名单。
- **原因**：刷新令牌的前提就是 **Access Token 已过期**；如果刷新接口要求认证，那它永远拿不到有效令牌 —— 逻辑自相矛盾。
- **面试话术**："很多实现只把 `/auth/login` 放行，结果刷新接口形同虚设（Access Token 过期后根本调不动）。刷新的语义决定了它必须免认证。"

### 6.3 多模块 reactor 的 jar 陷阱

- **现象**：`mvn -pl link-auth package` 打出的 fat jar 启动报 `NoClassDefFoundError`（找不到公共模块的类）。
- **原因**：`-pl` 不带 `-am` 时，依赖模块从**本地仓库**解析，而本地仓库里是**改名前的旧 jar**，被 repackage 打进了包。
- **解决**：带 `-am`，或先 `mvn install` 刷新本地仓库。
- **面试话术**："遇到'编译能过、跑起来缺类'，先怀疑构建产物不是最新的——多模块下 `-pl` 少了 `-am`，依赖可能取到本地仓库里的旧版本。"

### 6.4 敏感配置的"fail-fast"不能只靠去掉默认值

- **结论**：`application.yml` 里写 `secret: ${MY_SECRET}`（不给默认值）**并不会**让应用在缺失时启动失败。
- **原因**：Spring Boot 绑定配置时对**无法解析的占位符默认原样保留**，`secret` 会变成字面量字符串 `"${MY_SECRET}"`。它长度足够、能通过 HMAC 强度检查，于是**应用照常启动，并用一个可预测的密钥签发令牌**——比"配一个公开默认值"更危险（攻击者连默认值都不用猜）。
- **解决**：在配置类里加启动期校验（`@PostConstruct`）：空白 / 含 `${` / 强度不足一律抛异常拒绝启动。
- **面试话术**："敏感配置我做了 fail-fast：不能只指望'不写默认值就会报错'，实测 Spring 会把解析不了的占位符原样保留，等于用了一个可预测的密钥。所以我加了启动期校验，宁可起不来也不能用弱密钥上线。"

## 八、注册中心与配置中心（V2 实践）

### 8.1 配置中心的"能启动"和"能用"是两件事

- **结论**：容错要分三层做，少一层就会出现"服务活着但等于死了"。
  ① `spring.config.import=optional:nacos:...` —— 配置导入失败不致命；
  ② `spring.cloud.nacos.discovery.fail-fast: false` —— 注册失败不阻断启动（**SCA 默认是 `true`**，不设就会启动失败）；
  ③ **代码级关键配置兜底** —— 白名单在配置中心挂掉时若变成空列表，会把 `/auth/login` 也拦成 401，**登录被锁死**，所以代码里保留最小可用白名单。
- **面试话术**："容错不是'能启动'就够了。我第一版只加了 `optional:`，结果 Nacos 停掉后服务确实能起来，但配置全空——白名单空 = 登录被拦。后来补了 `fail-fast:false` 和代码级兜底白名单。"

### 8.2 配置变更的"假成功"最危险

- **现象**：日志打出 `[Nacos Config] Load config[dataId=link-auth.yaml] success`，紧接着 `ERROR ... YAMLException: MalformedInputException`；应用照常启动，但用的是默认配置。
- **原理**：`Load config success` 只表示"HTTP 取到了内容"，**不代表内容能被解析**。解析失败时 SCA 降级为默认值继续启动——于是配置静默失效。
- **对策**：发布配置后**回读校验**（拉回内容、按严格 UTF-8 解码、与本地文件比对），而不是信任发布接口的返回。
- **面试话术**："配置中心的坑在于它是'软失败'。我不会只看发布成功，而是回读校验一遍——就像发布后要做冒烟，而不是相信构建成功。"

### 8.3 编码问题在"发布端"和"消费端"都会发生

- **发布端**：PowerShell 5.1 的 `Invoke-WebRequest -Body <hashtable>` 用**系统默认编码（GBK）**拼表单体，把中文配置写成了 GBK 字节 → 修法是手工用 `EscapeDataString` 构造纯 ASCII 表单体。
- **消费端**：**JDK 17 + 中文 Windows 的默认字符集是 GBK**，SCA 对配置字符串做无参 `.getBytes()` 时转成 GBK，而 YAML 解析器按 UTF-8 读 → 修法是启动加 `-Dfile.encoding=UTF-8`（JDK 18+ 默认 UTF-8，问题消失）。
- **面试话术**："中文配置在分布式配置里是高危项。我踩了两次：一次是发布端（脚本按 GBK 编码），一次是消费端（JVM 默认字符集）。排查时先确认'Nacos 里存的字节是不是 UTF-8'，再确认'客户端按什么编码读'。"

### 8.4 区分"可动态刷新"与"必须重启"

- **可刷新**：`@ConfigurationProperties` 绑定的字段（如 `link.core.cache.ttl-seconds`）——配置发布后 Spring Cloud 的 rebind 机制会更新到 Bean 上。
- **必须重启**：`@ConditionalOnProperty` 驱动的开关（如 `id-generator-type`、`mq.enabled`）——它决定**启动时装配哪个 Bean**，改配置只能下次启动生效。
- **仍值得放配置中心**：因为"改配置 + 重启"比"改代码 + 重新打包发布"轻得多。
- **面试话术**："配置中心不是万能的。条件装配类开关改完要重启，所以做'动态刷新'演示时我特意选了运行时读取的 TTL 配置，而不是 `@ConditionalOnProperty` 的开关——否则就是在演示一个假象。"

### 8.5 配置中心的自举顺序

- **结论**：`spring.config.import` 与 `spring.cloud.nacos.server-addr` **必须在本地可解析**，不能放进配置中心自己。
- **原理**：否则形成循环依赖——"要拿配置得先连上配置中心，要连上配置中心得先有配置"。
- **面试话术**："配置中心的地址是引导配置，只能放本地。这是经典的 bootstrap 顺序问题。"

### 8.6 配置即代码

- **结论**：配置内容入 git（`deploy/nacos/config/*.yaml`）+ 用 Nacos OpenAPI 一键发布（`deploy/nacos/import-configs.ps1`）+ 发布后回读校验。
- **原理**：只在控制台手点，换机/重建环境就全丢、改动无迹可查、无法 code review。
- **面试话术**："我把 Nacos 配置也当代码管理：内容在 git 里，用脚本发布，发布后回读校验。这样重建环境是一条命令，配置变更也能评审。"
