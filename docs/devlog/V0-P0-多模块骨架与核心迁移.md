# V0（P0）多模块骨架与短链核心迁移

> 日期：2026-10-15 ｜ 版本：V0 ｜ 对应阶段：P0
> 一句话：把单体短链系统（AAE-short-link）无损搬进多模块仓库，建好微服务地基。

---

## 1. 做了什么

按"三个安全点"顺序执行（一次只引入一个变量）：

1. **安全点一·基线**：在 AAE 原仓库 `mvn clean test`，拿到基线数字。
2. **建骨架**：新建 `link-platform` 父工程（packaging=pom）+ 5 个子模块（common/gateway/auth/core/stats）共 6 个 pom。
3. **安全点二·复制**：把 AAE 的 72 个主类 + 28 个测试类 + 资源原样复制到 `link-core`（一行 import 不改），再跑测试验证"复制无损"。
4. **安全点三·抽取**：把 4 个公共类上移到 `link-common`（包名不变，零 import 改动），新增 2 个占位类，再跑测试。
5. **骨架**：建 gateway/auth/stats 三个最小骨架（启动类 + 配置）。
6. **环境隔离**：新建 `link_platform` 空库（不复制数据）、Redis 换 db 1、MQ 拓扑名加 `link.` 前缀。
7. **文档**：写需求架构文档、本开发日志。

## 3. 决策与理由

| # | 决策 | 理由（含"解决了上一版什么痛点"） |
|---|---|---|
| D1 | link-core 包名保留 `com.shortlink.*` | 涉及 100 个文件，重命名 diff 大到无法二分定位；先拿全绿基线，规范化留作独立 commit |
| D2 | 统计代码留 link-core | `RedirectServiceImpl` 依赖 `VisitRecorder`，硬抽会产生 core↔stats 循环依赖；P5 做 Kafka 时再抽 |
| D3 | Boot 3.2.5 + Cloud 2023.0.3 + SCA 2023.0.3.2 | 不改 AAE 的 Boot 版本，迁移只引入"模块化"一个变量 |
| D4 | 骨架模块仅编译通过 | P0 硬指标是"编译 + 198 单测"，未接 Nacos 时要求可启动是假失败 |
| D5 | 复制而非移动 | AAE 要原样保留，作为 P7 压测对比基线与面试演进故事本体 |
| D6 | 端口 gateway 8080/auth 8081/core 8082/stats 8083 | AAE 已占 8080 |
| D7 | 依赖方向 common ← core/gateway/auth/stats 单向 | 保证后续 auth/gateway 复用 common 而不污染 core |
| D8 | 环境隔离（新库/Redis db1/MQ 前缀） | 两个项目要能同时跑；P4 加 tenant_id 不能污染 AAE 基线 |

**计划执行中的两处修正（比原方案更正确的取舍）**：

- **R1｜`DegradedException` 改搬 common**：原计划让它留 core，但实测发现 `GlobalExceptionHandler` 第 42 行 `@ExceptionHandler(DegradedException.class)` 引用了它。只搬 handler 不搬异常会形成 `common → core` 反向依赖。它是纯 `RuntimeException`，零依赖，搬走零成本。
- **R2｜util 三件套留 core**：原计划把 `ClientIpResolver/RefererParser/UserAgentParser` 抽到 common。但 `ClientIpResolver` 依赖 `jakarta.servlet.http.HttpServletRequest`（servlet 专属，WebFlux 网关里不存在这个类），放 common 会把 servlet 依赖拖进网关；且三个工具类只被统计链路用（P0 统计留在 core），抽走才是"为抽而抽"。

## 4. 踩坑

| # | 现象 | 原因 | 解决 |
|---|---|---|---|
| 1 | 抽取 `GlobalExceptionHandler` 后 link-common 编译失败，5 个错误 | `MethodArgumentNotValidException` 继承自 `spring-context` 的 `BindException`，而 `spring-web` 不传递 `spring-context`；`@Slf4j` 生成的 `log` 字段需要 `slf4j-api`，它也没被带进来 | link-common 显式加 `spring-context` + `slf4j-api`（其余 3 个"找不到符号"是类型解析失败的级联报错） |
| 2 | 基线不是"198 全绿"，而是 1 个跳过 | `IdGeneratorBenchmarkTest` 带 `@EnabledIfSystemProperty(shortlink.benchmark=true)`，**设计上默认不跑**（压测基准需 MySQL/Redis） | 无需修复；验收口径订正为"198 run / 0 fail / 0 error / 1 skip（设计性跳过）" |
| 3 | gateway 依赖树出现 `tomcat-embed-el` | 它来自 `spring-cloud-gateway-server → spring-boot-starter-validation`，是**EL 表达式库**，不是 Servlet 容器 | 确认红线未破：无 `spring-webmvc`、无 `tomcat-embed-core`、无 `jakarta.servlet`；`tomcat-embed-el` 无害，无需处理 |

**预防未踩（靠计划前置规避）**：`spring-boot-maven-plugin` 放 parent 的 `pluginManagement` 而非 `build/plugins`——放错会让 link-common 也被 repackage 报 `Unable to find main class`。

## 6. 学到了什么（面试要点）

1. **"怎么解耦"的真答案**：不是"把代码搬进 common 就叫解耦"，而是"公共模块的最小依赖集合"。`link-common` 只依赖 `spring-web + spring-context + slf4j-api + jackson + lombok`，**不碰 starter-web**——因为 gateway 是 WebFlux，starter-web 会把 Tomcat 拖进来。
2. **包名不变 ⇒ 零 import 改动**：把类在模块间搬家但保留 `com.shortlink.common.*` 包名，消费方 import 一行都不用改。这是本次"无损迁移"能成立的关键技巧。
3. **"为抽而抽"的边界**：`ClientIpResolver` 是 servlet 专属、三个 util 只被统计链路用——抽到 common 反而是负担。边界感比"抽得多"更重要。
4. **配置 vs 常量的取舍**：RabbitMQ 拓扑名可配置（读 `ShortLinkProperties`），Redis key 前缀却硬编码在 `CacheKeyBuilder`——后者只能靠换 Redis db 隔离。这是"哪些该做成配置、哪些该固化"的活教材。
5. **诚实记录测试数字**：198 里有 1 个是"设计性跳过"（压测基准），不是"全绿无跳过"。面试讲数据要精确到 skip 这种细节。
